Why We Chose Docker Over SaaS for a 30-Agent AI Stack

We could have built a managed cloud platform. We chose Docker Compose instead. Here's the reasoning — and what that decision forced us to get right.

May 6, 2026 · ClawHQ

When we started building ClawHQ, the obvious move was a managed SaaS. Hosted infrastructure, usage-based billing, no ops burden for the user. That's what every AI tooling company was shipping in 2025.

We went the other direction: a single docker compose up that runs everything on your hardware. Here's why — and why we think more AI infrastructure will follow.

The data residency problem nobody talks about

AI agents are different from other SaaS tools because of what they touch. A Slack integration reads messages. A GitHub integration reads code. A support agent reads customer tickets. A research agent reads internal documents.

That's not a narrow data footprint — that's everything. And every piece of that data flowing through a third-party cloud means you're making a trust decision you can't audit.

For enterprise teams, this isn't abstract. It's GDPR, HIPAA, CMMC, or simply "our security team will never approve it." We talked to teams who wanted to run AI agents on internal data and couldn't find a platform that didn't require sending that data somewhere. So they were handwriting agent scripts instead.

Self-hosted Docker solves this cleanly. The agents run on your infrastructure. The data never leaves. There's no policy exception to write, no DPA to negotiate, no audit finding to remediate.

What you actually pay for with SaaS AI platforms

The typical AI agent SaaS charges per seat, per message, or per execution — and then separately for the underlying model calls. At scale, you're paying two margins: theirs and the model provider's.

Consider a 20-person engineering team using an AI agent platform at $50/seat/month. That's $1,000/month before a single model call. If each team member generates 500 agent interactions per month, and each interaction costs $0.01 in model tokens, that's another $100. But the platform has already priced in their margin on that too — you're actually paying closer to $300 in effective token costs, bundled.

With self-hosted Docker and BYOK (bring your own API key), the math is different:

Managed SaaS (20 seats)

  • $50/seat × 20 = $1,000/mo
  • Bundled model costs (~$300/mo effective)
  • Data leaves your infrastructure
  • Vendor controls uptime and pricing
  • Total: ~$1,300/mo

ClawHQ self-hosted

  • $0 for the platform (MIT)
  • Direct model costs: ~$100/mo
  • VPS/server: ~$20–40/mo
  • Data stays on your infrastructure
  • Total: ~$120–140/mo

The cost argument alone isn't why we made the decision — but it's a real forcing function for teams who are already paying per-seat for five other tools.

The architecture problem with cloud-native agent platforms

When you build for SaaS, you design your agent system around shared infrastructure: multi-tenant databases, shared message queues, rate-limited API gateways. The platform has to work for everyone, which means it's optimized for no one.

The most common complaints we heard about existing platforms were about configuration limits — you couldn't change the system prompt past a certain length, couldn't add custom tools without an enterprise tier, couldn't control how agents communicated with each other. These weren't bugs. They were the inevitable consequence of building on shared infrastructure that has to be protected from abuse.

Docker changes that constraint entirely. When you self-host, you own the stack. You can:

  • Mount a custom agents/ directory and override any default behavior
  • Add tools via YAML without touching the platform code
  • Run any model provider — not just the ones the platform decided to support
  • Adjust resource limits per agent based on actual workload
  • Integrate with internal services that are never on the public internet

That last one matters more than it looks. Most enterprise teams have internal APIs, databases, and services that don't have public URLs. A cloud-hosted agent can't reach them. A self-hosted agent running inside your network can.

What Docker-first forced us to get right

The honest version of this story is that self-hosted is harder to build well than SaaS. You lose observability (you can't see into customer deployments), you can't push hot fixes (customers control their update cycle), and you have to make the setup experience so good that someone running it for the first time doesn't give up.

That constraint was useful. It meant we couldn't paper over configuration complexity with a nice UI — we had to eliminate the complexity. It meant we couldn't rely on "contact support" when something broke — we had to build the health monitoring and debugging tools that let users diagnose issues themselves.

What we shipped to make self-hosting actually work

A real-time health dashboard with per-service sparklines. An update checker that compares your deployed commit SHA against main and shows the diff. An install script that handles environment setup, validates dependencies, and gives you a working stack. A structured error format that tells you which service failed and what to check. These aren't features — they're the cost of shipping a self-hosted product you'd actually want to use.

The model provider question

SaaS AI platforms have a business reason to limit your model choices: they're often reselling API access, and locking you to specific providers protects that margin. That's fine for them; it's a real constraint for you.

We support 27 providers natively — Anthropic, OpenAI, Groq, Gemini, DeepSeek, Mistral, Ollama (local), and 20+ more. Adding a new provider is a YAML entry. You use your own keys, your own pricing tiers, your own rate limits.

For teams that have negotiated enterprise contracts with a specific model provider, or that want to run a local model for certain agents and a frontier model for others, this flexibility isn't a nice-to-have. It's a requirement.

When self-hosted is the wrong answer

This isn't a universal argument for self-hosting everything. If you have no infrastructure team, no Docker experience, and your primary goal is getting something working in the next hour — a managed SaaS will serve you better initially.

Our own hosted offering (ClawHQ Cloud) exists for exactly that case. But even there, we've designed it so that migrating to self-hosted is a single docker compose up — your data is yours, the schema is open, and there's no lock-in to escape.

The default choice for any serious team handling internal data should be self-hosted. Not because cloud is bad — because the trust model of sending your internal context to a third party's servers is harder to justify the more agents you're running and the deeper they reach into your systems.
