How ClawHQ Routes Tasks Across 27 LLM Providers

Not every task needs GPT-4o. Not every task can use a local model. Here's how the model router decides which provider runs each agent call — and what we learned building it.

May 6, 2026 · ClawHQ

The most common question we get after "how do I install it" is "how does it decide which model to use." The answer is less magical than people expect — and more useful.

ClawHQ's model router is a layer that sits between every agent and the LLM it calls. It makes a routing decision on each request based on four things: the task type, the budget state, a learned success table, and a fallback chain. Here's how each works.

Why routing matters at all

If you're running 30 agents handling different kinds of work — code review, customer support, research, summarization, image analysis — you're paying frontier model prices for tasks that don't need frontier model quality. A support agent answering FAQ questions doesn't need the same model as a security auditor analyzing a potential vulnerability.

The cost difference is significant. At current pricing, a well-classified task that routes to Groq Llama 3 instead of Claude Opus costs roughly 40× less per token. If half your agent calls are classification, summarization, or structured extraction tasks that an 8B model handles just as well — your monthly bill is meaningfully different.

More importantly: local models (via Ollama) cost zero per token. If a task can run locally without quality regression, it should.

Layer 1: Task type detection

Before the router decides on a model, it classifies the incoming task. The classification is done by a small, fast model (currently Groq Llama 3.1 8B — fast enough that the classification overhead is negligible). The classifier assigns one of several task types:

Task typeExamplesDefault tier
classificationIntent detection, routing decisions, tag assignmentFast (Groq / local)
extractionStructured data from unstructured text, JSON parsingFast (Groq / local)
summarizationDocument compression, digest generation, meeting notesBalanced (Gemini Flash)
generationDrafting, writing, creative outputBalanced (Gemini Flash / GPT-4o-mini)
reasoningMulti-step problems, code generation, analysisFrontier (Claude / GPT-4o)
multimodalImage analysis, screenshot reading, document OCRFrontier (Claude / GPT-4V)
codeCode review, debugging, refactoring, test generationFrontier (Claude / GPT-4o)

The task type is the primary signal. A classification task will never be sent to a frontier model by default, regardless of which agent initiated it.

Layer 2: Budget state

If you've configured a monthly budget cap (in the Budget page), the router reads current spend before every call. As you approach the cap, the router progressively downgrades:

  • Under 80% of budget: use the default model for the task type
  • 80–95% of budget: step down one tier (frontier → balanced, balanced → fast)
  • Over 95% of budget: route all non-critical tasks to local Ollama if available; block frontier calls

This is configurable — you can set different thresholds per agent, or exempt specific agents from budget fallback entirely. A security auditor agent probably shouldn't be downgraded when you're 95% through budget; a weekly briefing agent probably should.

Layer 3: The success rate table

This is the part that improves over time. Every model call is logged with its outcome: did the response parse correctly, did the agent complete its task, did the user approve the output (where applicable). The router maintains a per-(task type, provider) success rate table.

If Groq starts returning malformed JSON on extraction tasks at a higher rate than Gemini Flash, the router shifts weight toward Gemini Flash for extraction automatically. No config change needed.

What "success" means

For structured output tasks (extraction, classification), success is clean JSON that passes schema validation. For generation tasks, success is a non-empty, non-truncated response. For tool-calling tasks, success is a valid tool call the agent can execute. The router doesn't try to judge quality — only parseable completeness. Quality evaluation is a harder problem we haven't solved.

The success table resets weekly by default. A provider having a bad Tuesday shouldn't permanently hurt its routing weight.

Layer 4: The fallback chain

If the selected provider returns an error — rate limit, timeout, API outage — the router doesn't surface that error to the agent. It falls back immediately to the next provider in the chain for that task type. The chain looks like this by default:

reasoning: [claude-sonnet, gpt-4o, gemini-pro, groq-llama3-70b]
generation: [gemini-flash, gpt-4o-mini, groq-llama3-70b, ollama-llama3]
fast:       [groq-llama3-8b, ollama-llama3, gemini-flash]

You configure the chains in settings/model-router in the dashboard. The defaults are opinionated — Groq first for speed-sensitive tasks because their inference is consistently the fastest — but you can reorder based on your provider relationships and pricing agreements.

If all providers in a chain fail, the router fires a webhook (if configured) and returns a structured error to the agent. The agent can handle it gracefully — most are configured to retry once before reporting failure to the channel.

Provider-specific handling

A few providers have idiosyncrasies the router handles transparently:

Ollama (local): The router pings localhost:11434/api/tags before adding Ollama to any chain. If it's not running, Ollama is excluded from routing decisions silently. No error, no config change needed.

Groq: Aggressive rate limits at the free tier (30 req/min). The router tracks Groq request timestamps and holds calls to stay under the limit rather than hitting 429s and burning fallback cycles.

Azure OpenAI: Endpoint URLs and deployment names vary by customer. Azure-hosted models are configured separately from OpenAI proper, with their own chain position. A team using Azure for compliance reasons can point all "OpenAI" calls at their Azure endpoint with one config change.

Anthropic tool use: Claude's tool use implementation is different from OpenAI's function calling schema. The router normalizes tool definitions before sending to each provider so agents don't need to know which model they're talking to.

What we got wrong initially

The first version of the router classified at the agent level — each agent was assigned one model. The code review agent used Claude, the support agent used GPT-4o-mini. Simple, predictable, wrong.

The problem is that agents handle heterogeneous tasks. The support agent answering "what's your refund policy" is a lookup task — fast model is fine. The same agent handling "why is my OAuth integration failing" is a debugging task that benefits from a stronger model. Agent-level routing throws away that signal.

Task-level routing is more complex to implement but the right abstraction. The classification step adds ~200ms of latency on the first call, cached for repeated similar requests in the same session.

Configuring it

The router is configured in .env (API keys) and the dashboard's Model Router settings page (chain order, budget thresholds, per-agent overrides). The default config works out of the box with any combination of keys you provide — if you only have an Anthropic key, every task routes to Claude. Add a Groq key and fast tasks shift automatically.

There's no required configuration. Zero keys = no routing, agents won't run. One key = everything routes there. Multiple keys = the router does its job.
